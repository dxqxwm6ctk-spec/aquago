# نشر AquaGo على Railway

دليل عملي لرفع الباكند. ملفات النشر (`Dockerfile`، `railway.json`،
`docker-migrate.sh`) جاهزة ولا تحتاج تعديلاً — ما يلي هو ما يُضبط في لوحة
Railway نفسها.

> **قبل أي شيء:** بعد ضبط المتغيّرات، افحصها بـ
> `cd backend && npm run check:env`. يمسك الفخاخ الصامتة — أهمّها متغيّر
> يبدو معرَّفاً في اللوحة وفارغ في الحاوية.

---

## ١) الخدمات الأربع

| # | الخدمة | النوع | الاسم المقترح |
|---|--------|------|----------------|
| 1 | PostgreSQL | Database (من قوالب Railway) | `Postgres` |
| 2 | Redis | Database (من قوالب Railway) | `Redis` |
| 3 | الـAPI | من مستودع GitHub | `api` |
| 4 | العامل | **نفس** المستودع | `worker` |

**الأسماء ليست تجميلاً.** مراجع المتغيّرات تُكتب بالاسم حرفياً
(`${{Postgres.DATABASE_URL}}`)، ومرجعٌ لاسم خاطئ **يُستبدل بسلسلة فارغة
بصمت** — لا خطأ في اللوحة ولا في البناء. إن سمّيت خدمة القاعدة
`postgres-db` مثلاً، فالمرجع الصحيح `${{postgres-db.DATABASE_URL}}`.

### إعداد خدمتَي `api` و `worker`

كلتاهما من نفس المستودع ونفس الصورة — الفرق متغيّر `ROLE` وحده.

في **Settings** لكل منهما:

- **Root Directory:** `backend`
- **Config File:**
  - `api` → `railway.json`
  - `worker` → `railway.worker.json`

الملفان مختلفان عمداً:

| | `railway.json` (api) | `railway.worker.json` |
|---|---|---|
| `preDeployCommand` | `sh docker-migrate.sh` | — |
| `healthcheckPath` | `/api/health/ready` | — |

- **الهجرة على الـapi وحدها:** لو حملها الملفان لتسابقت خطوتا هجرة على قفل
  Prisma الاستشاري في كل نشر. مرة واحدة تكفي — والقاعدة مشتركة.
- **لا فحص صحّة للعامل:** لا يفتح منفذ HTTP إطلاقاً
  (`createApplicationContext` بلا مستمع). فحصه مُعرَّف داخل `Dockerfile`
  عبر `HEALTHCHECK` الذي يتفرّع على `ROLE`. لو ضُبط `healthcheckPath` له
  لفشل كل نشر على مهلة انتظارٍ لمنفذٍ لن يُفتح.

## ٢) المتغيّرات

### أ. مشتركة بين `api` و `worker` — كلاهما يحتاجها

| المتغيّر | القيمة | لماذا |
|---------|--------|-------|
| `NODE_ENV` | `production` | يُفعّل حراسات الإنتاج. بدونه يُقبل سرّ JWT الافتراضي ويُفتح CORS لأي أصل. |
| `DATABASE_URL_V2` | `${{Postgres.DATABASE_URL}}` | القاعدة. يُقبل `DATABASE_URL` بديلاً — يشتقّه `docker-common.sh`. |
| `REDIS_URL` | `${{Redis.REDIS_URL}}` | الطوابير. **اُنظر التحذير أدناه.** |
| `JWT_SECRET` | ولّده: `openssl rand -base64 48` | نفسه في الخدمتين حرفياً، وإلا رفض العامل توكنات الـapi. |
| `STORAGE_PROVIDER` | `s3` أو `local` | لا افتراضي — الإقلاع يفشل بدونه. اُنظر §٣. |
| `FIREBASE_SERVICE_ACCOUNT_BASE64` | ملف حساب الخدمة JSON بترميز base64 في سطر واحد | دخول جوجل/آبل **والإشعارات**. بدونه يفشل الدخول كلياً. |
| `API_INSTANCE_COUNT` | `1` | يطابق `numReplicas`. اُنظر §٤. |
| `WORKER_INSTANCE_COUNT` | `1` | كذلك. |
| `DB_MAX_CONNECTIONS` | حدّ خطة قاعدتك | من لوحة Postgres. الافتراضي 90 يناسب قاعدة بـ100. |

**⚠️ `REDIS_URL` هو الفخّ الأخطر في هذه القائمة.** كل المتغيّرات الأخرى
توقف الإقلاع إن غابت — هذا وحده **يقع على `redis://localhost:6379`
بصمت**. الخدمة تُقلع سليمة، تجتاز فحص الصحّة، ويبدو كل شيء أخضر — ثم لا
يعمل أي طابور ولا مهمة مجدولة، ولا يظهر ذلك حتى أول طلب حقيقي.

توليد السرّ والترميز:

```bash
openssl rand -base64 48                                   # JWT_SECRET
base64 -w0 aqua-go-....json                               # Linux/Git Bash
[Convert]::ToBase64String([IO.File]::ReadAllBytes("x.json"))  # PowerShell
```

الترميز **في سطر واحد** بلا أسطر جديدة — القيمة المكسورة تفشل بـ«ليس JSON
صالحاً بعد فكّ base64».

### ب. على `api` وحدها

| المتغيّر | القيمة | لماذا |
|---------|--------|-------|
| `ROLE` | `api` | (افتراضي، لكن التصريح يُغني عن التخمين) |
| `PORT` | `${{PORT}}` | يحقنه Railway. لا تكتب رقماً ثابتاً. |
| `CORS_ORIGINS` | نطاقات لوحاتك مفصولة بفواصل | **يوقف الإقلاع** في الإنتاج إن غاب. لا يُقبل `*`. |

مثال: `https://admin.aquago.jo,https://agency.aquago.jo`

### ج. على `worker` وحدها

| المتغيّر | القيمة |
|---------|--------|
| `ROLE` | `worker` |

`CORS_ORIGINS` و`PORT` بلا معنى له — لا يخدم طلبات.

### د. اختيارية — غيابها يعطّل ميزتها بهدوء

| المتغيّر | الافتراضي | أثر الغياب |
|---------|-----------|------------|
| `FCM_PROVIDER` | `dev` | **لا إشعارات Push فعلية.** اجعله `firebase` للإنتاج. |
| `WHATSAPP_PROVIDER` | `dev` | لا رسائل واتساب (يحتاج `WHATSAPP_API_URL` و`WHATSAPP_API_KEY`). |
| `TELEGRAM_PROVIDER` | `dev` | لا تنبيهات أدمن (يحتاج `TELEGRAM_BOT_TOKEN` و`TELEGRAM_CHAT_ID`). |
| `METRICS_TOKEN` | — | نقطة `/api/v2/metrics` **مغلقة** — وهذا آمن ومقصود. عرّفه فقط إن أردت كشفها لجامع مقاييس. |
| `LOG_FORMAT` | `json` | مناسب لسجلّات Railway كما هو. |
| `REDIS_TLS` | — | `true` فقط لمزوّد يفرض TLS ويعطي رابط `redis://`. Redis داخل Railway لا يحتاجه. |

### هـ. لا تضعها في الإنتاج أبداً

| المتغيّر | لماذا |
|---------|-------|
| `AUTH_DEV_LOGIN=1` | دخول **يتجاوز التحقق كلياً**. |
| `OTP_MASTER_CODE` | رمز تحقق ثابت يقبله الخادم. (يتجاهله الكود تلقائياً حين `NODE_ENV=production`، لكن وجوده في اللوحة يعني تفعيله لحظة تغيير `NODE_ENV`.) |

## ٣) التخزين والـVolumes

### القرار: هل تحتاج volume؟

**يعتمد على `STORAGE_PROVIDER` وحده:**

#### إن اخترت `s3` ← **لا volume إطلاقاً**

الملفات تذهب إلى مزوّد خارجي، وقرص الحاوية يبقى عابراً كما ينبغي. هذا
**الخيار الموصى به**.

متغيّراته (على `api` و`worker` معاً — كلاهما يقرأ ويكتب):

| المتغيّر | مثال |
|---------|------|
| `S3_ENDPOINT` | `https://fra1.digitaloceanspaces.com` |
| `S3_BUCKET` | `aquago` |
| `S3_ACCESS_KEY` | من لوحة المزوّد |
| `S3_SECRET_KEY` | من لوحة المزوّد |
| `S3_REGION` | `fra1` (افتراضي `us-east-1`) |
| `S3_PUBLIC_URL` | اختياري — رابط CDN عام. بدونه تُخدَّم الملفات عبر الخادم (يعمل، لكن أبطأ). |

يعمل مع أي مزوّد متوافق مع S3 (DigitalOcean Spaces، Cloudflare R2،
Backblaze B2، AWS S3) — الكود يضبط `forcePathStyle` لذلك.

#### إن اخترت `local` ← **volume إلزامي، وإلا ضاعت الملفات**

قرص حاوية Railway **عابر**: كل نشر يبني حاوية جديدة، وكل ما كُتب على قرص
السابقة يختفي. بلا volume تفقد عند كل نشر:

- وثائق انضمام الوكالات والسائقين (`onboarding-docs`)
- الصور المرفوعة من اللوحات (`uploaded-images`)

إعداد الـvolume:

| الحقل | القيمة |
|-------|--------|
| الخدمة | `api` |
| Mount path | `/app/storage-dev` |
| الحجم | 1GB يكفي للبداية |

ثم على `api`: `STORAGE_LOCAL_PATH=/app/storage-dev`

**قيد يجعل هذا الخيار مؤقتاً:** volume الواحد يُركَّب على خدمة واحدة فقط.
فإن احتاج العامل قراءة تلك الملفات لاحقاً، أو أردت أكثر من نسخة API، لزم
الانتقال إلى `s3`.

> القيمة الافتراضية لو أُغفل `STORAGE_LOCAL_PATH` هي `./storage-dev` نسبةً
> إلى مجلد العمل (`/app`) — أي المسار نفسه. التصريح به يجعل تطابقه مع
> نقطة التركيب مقصوداً لا مصادفة.

### لا volume لقاعدة البيانات ولا لـRedis

خدمتا Railway المُدارتان تديران تخزينهما بنفسهما.

## ٤) عدد النسخ واتصالات القاعدة

`railway.json` يضبط `numReplicas: 1`، بينما `API_INSTANCE_COUNT` **افتراضيه
2** في الكود. المطابقة ليست تجميلاً — الرقم يقسم اتصالات القاعدة:

| القاعدة | `API_INSTANCE_COUNT` | نصيب كل عميل Prisma |
|---------|---------------------|---------------------|
| 100 اتصال | 2 (الافتراضي) | 13 |
| 100 اتصال | **1** (مطابق) | **20** |
| 22 اتصال | 2 | 2 |
| 22 اتصال | **1** | **4** |

القيمة الأعلى من الواقع تهدر سعةً موجودة (تعمل، لكن أضيق). الأخطر عكسها:
لو رفعت `numReplicas` لاحقاً بلا رفع `API_INSTANCE_COUNT`، تجاوزت الحاويات
مجتمعةً حدّ القاعدة — وعندها تفشل الاتصالات تحت الحمل تحديداً.

**القاعدة: أبقِ الرقمين متطابقين دائماً.**

الخطة الفعلية تُطبع في السجلّ عند كل إقلاع، فتحقّق منها بعد النشر:

```
v2 — تجمّع الاتصالات: 90 إجمالي، 20 محجوزة، 1 API + 1 Worker = 2 عملية…
```

## ٥) ترتيب النشر

1. أنشئ `Postgres` و`Redis` من قوالب Railway.
2. أنشئ `api` من المستودع → Root Directory: `backend`، Config: `railway.json`.
3. اضبط متغيّرات `api` (§٢-أ + §٢-ب) — لا تنشر بعد.
4. افحص: `cd backend && npm run check:env` (بنفس القيم محلياً في `.env`).
5. انشر `api`. **راقب السجلّ**، وابحث فيه عن:
   - `🗄️ تطبيق هجرات منصة v2...` ثم `✅ خطوة الهجرة اكتملت.`
   - `Firebase Admin مُهيَّأ — مشروع …`
   - `v2 — تجمّع الاتصالات: …` (طابق الأرقام مع §٤)
6. أنشئ `worker` من نفس المستودع → Config: `railway.worker.json`.
7. اضبط متغيّراته (§٢-أ + `ROLE=worker`) وانشره.
8. ولّد نطاقاً للـ`api` من **Settings → Networking → Generate Domain**.

### التحقق بعد النشر

```bash
curl https://<نطاقك>/api/health/ready     # 200
curl https://<نطاقك>/api/health           # تفصيل: القاعدة، Redis
```

ثم من التطبيق: ابنِ بـ
`--dart-define=AQUAGO_API_BASE=https://<نطاقك>` وجرّب تسجيل الدخول فعلياً
— هو المسار الذي يمرّ بالقاعدة وFirebase والتوكنات معاً.

## ٦) أعطال شائعة

| ما تراه | السبب |
|---------|-------|
| `DATABASE_URL_V2 فارغ أو غير معرَّف` | مرجع لاسم خدمة خاطئ — يُستبدل بفراغ بصمت. طابق الاسم حرفياً. |
| `JWT_SECRET غير معرَّف (أو لا يزال بالقيمة الافتراضية)` | لم يُضبط، أو بقي سرّ التطوير. |
| `CORS_ORIGINS غير معرَّف` | إلزامي في الإنتاج. |
| `STORAGE_PROVIDER=… غير معروف` | القيم المقبولة `local` أو `s3` فقط. |
| `تعذّر التحقق من حساب جوجل` **مع 503** | `FIREBASE_SERVICE_ACCOUNT_BASE64` غائب أو مكسور. (401 يعني توكن غير صالح — عطلٌ مختلف تماماً.) |
| كل شيء أخضر لكن لا طوابير ولا مهام مجدولة | `REDIS_URL` غائب ووقع على localhost. |
| الملفات المرفوعة تختفي بعد كل نشر | `STORAGE_PROVIDER=local` بلا volume. |
| فشل النشر على مهلة فحص الصحّة (خدمة `worker`) | ضُبط لها `healthcheckPath` — لا تفعل، لا تفتح منفذاً. |
| `P3005` في خطوة الهجرة | يُعالَج ذاتياً: يسجّل `0_init` كمُطبَّقة ثم يعيد المحاولة. |
